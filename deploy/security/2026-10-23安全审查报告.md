# detla 上线前安全审查

> 更新：本报告所述的代码级阻断项已完成修复并部署，隔离回归 45/45 通过。最新状态与剩余验收项见 [2026-10-24安全修复报告](./2026-10-24安全修复报告.md)。

**结论：本轮审查未通过，当前版本不具备正式开放注册、支付、充值和提现的条件。**

检查日期：2026-10-23。正式后端版本挂载自 `feature-releases/20261023-205419/backend/app.jar`。本轮只新增审计材料和本地忽略规则，没有修复或发布业务代码，没有修改正式数据库业务记录。此前的 UI、打手主页等改动保持原状。

发现的问题包含已经在同版本后端的独立环境中复现的越权、匿名写操作、登录验证缺失和资金一致性错误。不能把“页面能打开”或“支付、短信开关尚未开启”作为安全放行依据。任何一次审查都不能证明系统绝对没有漏洞。

## 微信支付、余额、退款、提现专项

当前正式环境 `WX_PAY_ENABLED=false`，数据库 `wx.pay.enabled=false`；未发现公开上传树内存在 PEM 证书文件。本轮没有发起真实扣款或退款。这能降低当前支付通道暴露，但不能替代修复。

已具备的控制：使用微信官方 Java SDK 的 `NotificationParser` 进行验签和解密；下单金额取后端支付单；客户端不直接决定充值赠送金额。**不能删除 SDK 验签来解决回调失败。**

除上表已复现问题外，下列为源码确认的设计缺陷，尚未使用真实商户做端到端验证：

- 回调先读取状态再更新，没有支付单行锁/条件更新保证唯一状态转换，余额采用读后写，缺乏可证明的并发幂等；仅判断 PAID 不足以覆盖重复、乱序、已退款通知等状态。
- 余额支付、提现、短信扣费、结算和退款使用的锁粒度不一致；部分 Redis 锁用固定值、固定过期时间并直接删除，缺少锁所有权校验。不能只依赖这类锁保护数据库资金。
- 退款申请接口返回后直接标记 REFUNDED，未区分处理中、成功、关闭和异常；没有完整退款回调/查单恢复。外部受理与本地事务提交之间也缺少恢复设计。
- 提现审核与订单结算用“先查询状态再改状态”的方式防重，缺少数据库原子抢占状态及钱包锁。并发审核、并发确认和其他钱包操作需要专项回归，不能宣称已复现双重入账。
- 金额从元转分存在 `intValue()/longValue()` 截断式转换，需要统一最多两位小数、正数、上限和精确整数转换；抽佣与队友分成需验证范围和总和。

微信要求通知验签失败使用失败 HTTP 状态，成功使用 200/204，并要求具备重复通知处理和查单机制，参见[微信支付普通支付通知文档](https://pay.wechatpay.cn/doc/v3/merchant/4013070368)。退款受理不代表最终到账，最终状态应来自退款通知或查单，参见[退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)。

接入前必须完成：正常支付、签名错误、解密错误、金额/币种/商户不符、重复和并发通知、取消后通知、支付后本地故障、退款 PROCESSING/SUCCESS/CLOSED、并发余额支出、重复提现审核，以及定时查单/账单对账的集成回归。真实商户、域名绑定、商户证书/公钥轮换、实际到账和对账本轮未验证。

## 登录、验证码和短信专项

**当前 H5 输入框虽然叫“验证码”，后端实现是固定配置码，不是真实短信验证码闭环。** 现有阿里云短信代码主要服务聊天提醒、订单指派和队友邀请；直接填入短信 AccessKey 并启用开关，不会自动获得安全的登录验证码能力。

正式短信开关 `sms.aliyun.enabled=false`，本轮未发任何短信。聊天短信服务具有成员校验、发送冷却和部分打手扣费控制，但其上游身份仍可被 `chatRole` 覆盖，不能把这套成员校验视为可靠的授权边界。

需要补齐或整改：

1. OTP 使用密码学安全随机数；服务端只保存摘要，绑定手机号、用途、请求编号和短有效期；验证和消费原子执行。注册、登录、换绑、找回分别隔离。
2. 手机号、IP、设备、账号及全站多层限速和日限额；失败次数上限；风险触发图形/滑块等人机验证；统一登录失败文案。短信平台频控不能替代应用层校验。
3. 管理/客服登录现有 BCrypt 与 5 次失败锁定 30 分钟可保留，但还需 IP 限速、统一失败信息、合理密码策略及管理员多因素验证；停用/改密立即撤销会话。
4. 服务商密钥应最小权限，禁止写入前端、源码或公开目录；后台读取密钥需脱敏，更新时区分“未修改”和清空；手机号、验证码和密钥不进入普通日志。
5. 聊天/业务提醒按业务事件设置幂等键与发送记录；防止重复事件或回滚重试重复扣费、重复发送；配置允许的服务商 endpoint；设置服务商预算和报警。
6. 验证错误/过期/重复使用验证码、暴力尝试、重复发码、伪造手机号、短信发送失败、超时重试与实际扣费；通过 mock 验证后，再在正式接入条件具备时做受控小规模验收。

服务商频控配置可参考[阿里云短信官方说明](https://www.alibabacloud.com/help/en/sms/user-guide/configure-messaging-limit)。本轮没有验证真实模板审核、签名、运营商送达率和费用结算。

## 页面、接口与数据安全的其他结果

- 唯一确定缺失的 API 路径：管理端 `delta-admin-ui/src/api/system.js:94` 的 `POST /system/notice/{id}/push`，后端 NoticeController 没有对应实现；独立环境调用得到业务 500。应实现授权和防重的推送流程，或移除对应入口。
- 64 个已注册路由均存在源文件。`pages-player/index/index.vue` 和 `pages/agreement/index.vue` 没有注册；当前访问入口需以 pages.json 为准。匿名页面检查不会覆盖登录后数据、真实参数及全部按钮交互，不能写成“所有页面功能通过”。
- 126 次线上匿名 GET 中，99 次返回业务 401，18 次业务 200，2 次业务 404，3 次业务 500，4 次为其他响应格式。探测使用 ID=0，不存在商品/文件的错误并非被归类为数据泄露；错误格式仍需统一。
- 普通用户和打手对 `/admin/**` 的 GET 检查没有发现未授权放行；客服可访问的聊天记录接口属于现有明确规则。对象级越权和缺少 PLAYER 角色约束仍按上表处理，前端路由守卫无法替代服务端授权。
- 个人资料更新直接绑定实体，仍应改用字段白名单 DTO；公开旧评价接口返回原始实体，应去掉用户 ID、订单 ID 等非展示字段。批量赋值、通知已读归属、分页上限需要补充负向回归。
- RichTextEditor 使用 `v-html`/`innerHTML` 展示内容，未见 HTML 白名单清洗。结合商品写权限过宽，存在存储型脚本注入风险；本轮没有让正式管理员打开恶意内容，也没有实施令牌窃取。服务端清洗、URL 协议白名单和前端安全渲染应同时处理。
- 线上接口文档可匿名访问，应在生产关闭或限制为运维入口；分页参数缺少统一上限，应防止单请求无界查询。没有做生产压力测试、端口暴力扫描或破坏性测试。
- CORS 实测反射任意测试 Origin，并允许 credentials。应只允许实际 H5、管理端域名；当前主要使用 Bearer 令牌，该配置本身不等同于浏览器会自动附带 localStorage 中的令牌。
- Redis 反序列化使用宽泛类型策略，需要缩小允许类型并核实用途。本轮 Redis 未向宿主机发布端口，没有确认可从公网控制 Redis 数据，不能直接认定已存在远程反序列化利用链。

# 平台自动退款技术方案

版本 V1.0　日期 2026年10月25日　项目基线 20261025-player-pricing

自动退款采用“未接单订单按规则自动退，已服务或有争议订单人工审核”的方式。复用现有余额支付和微信支付代码，补齐退款规则、独立退款单、超时任务和异常处理。以下为拟实施方案，不代表相关功能已经开发或开启。

## 1 实施范围

首期实现普通商品订单全额退款，包括用户取消未接单订单、付款后超时无人接单，以及管理员审核通过的未结算订单退款。自动退款只处理已确认支付成功、未开始服务、未结算且符合后台规则的订单。

首期不自动处理充值、入驻押金、打赏、已结算订单和部分退款。这些业务的资金与结算规则不同，需要单独设计，不能混用商品订单退款接口。

| 订单情况 | 默认处理方式 | 资金处理 |
| --- | --- | --- |
| 待付款 PENDING_PAYMENT | 到期取消 | 未确认付款前不退款 |
| 已付款待接单 PAID | 用户申请可自动退 | 退实际支付全额 |
| PAID 超过接单时限 | 定时任务自动申请 | 退实际支付全额 |
| 已指派 ASSIGNED | 默认转人工审核 | 审核通过后退款 |
| 已接单 ACCEPTED 或组队中 | 转人工审核 | 核实服务情况后处理 |
| 进行中或存在争议 | 转人工审核 | 不按未接单规则直接退 |
| 已完成或已结算 | 首期关闭自动退款 | 另行核对打手收益与平台资金 |

退款金额取原支付记录，不按当前商品价格重算。例如商品45元、指定打手涨价15%，实际支付51.75元，则全额退款51.75元。余额支付退平台余额；微信支付通过原支付交易原路退款。

## 2 现有能力与需要修改的部分

以下结论来自当前项目源码，属于实现现状核对，不等同于正式微信支付联调验收。

| 模块 | 当前已有能力 | 本次需要补充 |
| --- | --- | --- |
| 订单取消 | PAID 和 ASSIGNED 可进入退款流程 | 接入统一规则，避免旧入口绕过审核 |
| 余额退款 | 钱包入账及退款流水 | 按退款单幂等入账与独立记录 |
| 微信退款 | 退款申请、回调验签与解密 | 独立退款单、错误分级与人工处理入口 |
| 退款补偿 | 每30秒扫描微信退款中记录 | 分页调度、退避查询、告警及任务租约 |
| 支付记录 | 单条支付单保存退款金额和单号 | 新增退款明细及累计金额，避免覆盖历史 |
| 订单结算 | 确认完成后向打手钱包结算 | 审核中及退款中禁止结算 |

当前退款方法虽然接收退款金额，但订单更新主要按整单退款处理，因此不能直接把该方法当作完整的部分退款功能。部分退款须完成独立退款记录、累计可退校验和结算调整后再开放。

## 3 后台配置

新增“系统管理 → 自动退款设置”，以及“订单管理 → 退款记录”。退款设置只允许管理员修改，客服按授权额度审核，用户只能申请和查询自己的退款。

| 配置项 | 建议初始值 | 生效方式 |
| --- | --- | --- |
| 自动退款总开关 | 关闭 | 控制新自动申请 |
| 未接单取消自动退款 | 开启规则但随总开关关闭 | 仅适用 PAID 且无人接单 |
| 无人接单超时退款 | 关闭 | 管理员选择后开启 |
| 无人接单时限 | 15分钟示例 | 可配置，计时起点为支付成功时间 |
| 单笔自动退款上限 | 管理员设置 | 超额转人工审核 |
| 适用商品和分类 | 管理员选择 | 商品规则优先，未设置则继承全局 |
| 已指派及已接单订单 | 人工审核 | 不默认放入自动退款范围 |
| 异常通知 | 站内消息及后台待办 | 不依赖短信发送 |

支付成功时保存规则版本、规则快照及 auto_refund_at。后续修改规则默认只影响新付款订单，避免后台改为15分钟后批量退掉历史订单。指定打手和指定等级订单可以配置单独时限，但同样需要保存快照。

到期扫描建议每30秒执行一次，实际发起时间还受扫描及队列排队影响，不承诺到秒触发。总开关关闭后，停止新增自动退款，已提交的退款仍继续查询、回调入账和对账。

## 4 退款流程与状态

**申请阶段：** 用户取消或超时任务触发 → 锁定订单 → 复核支付、接单、结算及规则 → 创建退款单 → 占用可退金额 → 冻结订单操作 → 写入执行任务 → 提交数据库事务。

**执行阶段：** 余额退款在本地事务中完成钱包入账；微信退款由任务在申请事务提交后执行。不能在数据库长事务里等待微信接口，也不能仅依赖内存事件保存退款申请。

**确认阶段：** 收到有效退款结果或主动查询确认 → 幂等记录结果和流水 → 更新累计已退金额 → 更新订单及退款展示 → 发送站内通知。微信接口受理成功不代表退款已到账。[W1]

| 退款单状态 | 含义 | 后续处理 |
| --- | --- | --- |
| REVIEW_PENDING | 等待审核 | 审核通过或拒绝 |
| READY | 已批准，等待执行 | 领取任务并执行 |
| PROCESSING | 渠道处理中或结果待确认 | 回调及主动查单 |
| SUCCEEDED | 已确认退款成功 | 不可重复入账 |
| REJECTED | 审核拒绝，尚未执行 | 核对无其他冻结后恢复订单 |
| CLOSED | 渠道明确关闭且未退款 | 人工决定后续，保留原记录 |
| MANUAL_REQUIRED | 异常待人工处理 | 继续核查，禁止直接恢复接单 |

订单增加 refund_hold 冻结标记。审核中、执行中和结果不明时，禁止接单、指派、开始服务、确认完成、结算和新增打赏。首期全额退款进入 REFUNDING，确认全部退回后进入 REFUNDED。

退款失败不能直接把订单改回 PAID。必须先确定渠道未退款、没有其他在途退款及投诉冻结，再由明确的处理动作恢复；结果不明时持续冻结。

## 5 数据库设计

新增 refund_order 退款单和 refund_task 任务表，复用现有 operation_log、order_progress 和 transaction 记录操作与资金变化。所有金额使用 DECIMAL 和 Java BigDecimal，微信接口金额转换为整数分。

| 退款单字段 | 建议类型 | 用途 |
| --- | --- | --- |
| id 和 refund_no | BIGINT 和 VARCHAR(64) | 内部主键及唯一商户退款单号 |
| order_id 和 payment_id | BIGINT | 绑定原订单和原支付交易 |
| requester_type 和 requester_id | VARCHAR 和 BIGINT | 记录 USER、ADMIN、CS 或 SYSTEM |
| request_id | VARCHAR(64) | 请求幂等键，必填且非空 |
| trigger_type 和 reason_code | VARCHAR | 区分主动取消、超时和人工退款 |
| amount 和 currency | DECIMAL(12,2) 和 CHAR(3) | 锁定退款金额及币种 |
| status 和 channel_refund_id | VARCHAR | 本地状态及渠道退款号 |
| source_order_status | VARCHAR | 申请前的订单状态 |
| rule_snapshot | JSON | 保存生效规则与版本 |
| reviewed_by 和 reviewed_at | BIGINT 和 DATETIME | 审核人及审核时间 |
| last_error_code 和 last_error_message | VARCHAR | 脱敏后的异常原因 |
| created_at 和 succeeded_at | DATETIME | 申请及成功时间 |

payment 增加 refunded_amount 累计成功退款金额、refund_reserved_amount 在途占用金额。order 增加 refund_hold、refund_active_id、auto_refund_at 和 refund_rule_snapshot。审核待处理及结果不明的金额也计入占用，防止再次申请超退。

refund_task 保存 refund_id、task_type、status、attempts、next_run_at、lease_until 和 lease_token。任务类型区分发起退款、查询结果、发送通知；同一退款同类任务只保留一条，重新调度更新原任务。

**关键约束：** refund_no 全局唯一；申请人类型、申请人ID、request_id 组合唯一；任务的 refund_id 与 task_type 组合唯一。SYSTEM 的申请人ID使用约定的非空值，避免空值使组合唯一约束失效。

资金流水增加 refund_id，对退款入账建立唯一业务约束。幂等键重复但请求内容不同，应拒绝处理，不能返回另一笔订单的退款结果。退款记录不提供普通删除功能，错误操作通过可追溯的审批或冲正处理。

可退金额必须在锁住支付记录后计算：

```text
可退金额 = 原支付金额 - 累计成功退款 - 在途占用金额
0 < 本次申请金额 <= 可退金额
成功退款与在途占用之和，不得超过原支付金额
```

## 6 事务与防重复处理

锁顺序统一为订单、支付单、退款单、用户钱包；涉及多个打手钱包时按打手ID排序。既有支付、退款、打赏和结算路径也须核对锁顺序，避免仅新增代码遵守而旧代码产生死锁。

退款申请与抢单使用同一订单行作为串行化依据。超时任务不能根据扫描时的状态直接退款，进入事务后必须再次确认 PAID、player_id 为空、未结算且到期。如果打手先接单成功，该次自动退款退出；退款先冻结成功，后续抢单请求拒绝。

申请事务的处理示例：

```text
BEGIN
  SELECT order FOR UPDATE
  按当前身份校验权限，按规则快照复核退款资格
  查询幂等申请；存在则核对内容并返回原退款单
  SELECT payment FOR UPDATE
  检查是否已有活动退款，计算并预占可退金额
  INSERT refund_order
  UPDATE order SET refund_hold = 1, refund_active_id = ...
  INSERT refund_task
COMMIT
```

余额退款在一个事务内完成：锁退款单及钱包 → 检查成功状态及唯一流水 → 余额增加 → 写入退款流水 → 释放占用并增加已退金额 → 更新退款单及订单。任一步失败全部回滚。

微信回调与主动查单共用同一个结果处理方法。只有首次成功状态变更可以更新累计金额和产生通知；重复通知直接返回成功，不再次入账。任务使用可续期租约和领取版本，多实例或进程重启后可恢复，过期执行者不得覆盖新执行者的状态。

## 7 微信退款与异常补偿

退款执行前核对原微信交易已支付成功，校验商户、交易号和金额。使用固定的商户退款单号提交退款，接口为 POST /v3/refund/domestic/refunds。网络超时、限流或服务器异常先按原退款单号查询，再决定是否重试，禁止因为一次超时就生成新单号。[W1][W2]

回调继续复用微信支付官方 SDK 的验签与解密能力，核对原支付单、退款单号、交易号、币种及退款金额。回调接收路径沿用 /api/pay/wx/refund-notify，必须使用公网可访问的 HTTPS 地址。[W2]

| 异常类型 | 处理方式 |
| --- | --- |
| 网络超时或结果未知 | 保留占用，先查询原退款单 |
| 限流或服务端暂时异常 | 降低频率，原单原参数重试 |
| 商户退款资金不足 | 后台告警，补足资金后恢复原单处理 |
| 签名或商户配置错误 | 停止新增该渠道执行，通知管理员修复 |
| 渠道退款异常 ABNORMAL | 转人工处理，保留占用和冻结 |
| 回调缺失 | 主动查询补偿，以确认结果为准 |
| 渠道已成功但本地未提交 | 查单或重复回调再次幂等落账 |

查询采用退避策略：初期约每1分钟查一次，持续处理中超过5分钟后逐步延长至5、10、20、30分钟。达到平台告警时限后转人工待办，但仍保留低频查询，不把未知结果当作失败释放额度。[W1]

每日对照渠道账单及本地支付、退款记录生成差异清单。重点检查渠道成功而本地未成功、金额不符、长期在途和有退款但缺少流水等情况。人工补记须基于核验后的渠道结果，不能通过修改页面状态冒充到账。

## 8 结算与部分退款扩展

首期自动退款必须检查 settled 不等于1，且审核、退款冻结标记同时阻止确认完成及自动结算。自动确认、自动指派等直接执行 SQL 的任务也必须增加冻结条件，不能只改页面按钮。

第二期开放部分退款时，需要将服务履约状态和退款状态分开。部分退款成功不等于整单退款成功，应保留原支付金额，记录累计退款，并按明确规则处理剩余服务及结算。

例如订单支付100元、原抽佣10%，退款20元后，若约定按剩余80元结算，则平台佣金8元、打手总收益72元。多人订单按下单及分成快照重新核算，不能直接套用当前后台比例。固定金额分成导致收益不足时必须人工处理。

已结算订单需要记录平台、主打手、队友各自应承担的退款份额，并增加独立冲正流水。打手余额不足或已提现时，转人工处理或执行经批准的平台垫付方案，不允许静默扣成负数。订单退款与打赏退款分开处理，不自动连带撤销打赏。

## 9 接口与代码改造

以下均为建议新增接口，访问路径统一带现有 /api 前缀。用户身份和审核权限从登录态获取，不接受前端指定操作者身份；普通用户不能提交任意退款金额。

| 接口 | 作用 | 权限 |
| --- | --- | --- |
| POST /order/{id}/refunds | 申请整单退款，传 requestId 和原因 | 订单本人 |
| GET /order/{id}/refunds | 查询本人的退款进度 | 订单本人 |
| GET /admin/refunds | 查询退款单和异常记录 | 管理员及授权客服 |
| POST /admin/refunds/{id}/review | 通过或拒绝，保留审核原因 | 按额度授权 |
| POST /admin/refunds/{id}/retry | 核对渠道后恢复任务 | 管理员 |
| GET 或 PUT /admin/refund-settings | 读取或修改退款规则 | 管理员 |

用户申请示例：

```json
{"requestId":"唯一请求编号","reasonCode":"NO_LONGER_NEEDED"}
```

返回退款单号、申请金额、当前状态和处理说明。重复提交同一请求返回原记录。退款成功页面只读取服务端已确认结果；客服和打手端显示对应进度，隐藏用户支付身份及其他订单的私密字段。

**代码分工：** delta-order 负责订单资格与状态流转；delta-pay 新增 RefundApplicationService、RefundExecutionService、RefundTimeoutTask 和 RefundRecoveryTask；delta-system 管理规则；delta-admin 提供审核和异常处理；delta-mp 与 delta-admin-ui 增加进度和管理页面。

旧的取消、管理员退款及事件监听入口必须统一接入新规则，不能保留可以直接绕过规则的退款路径。已有 RefundEventListener 可用于同一事务内创建退款单和任务，实际微信请求在提交后执行。跨模块继续通过公共事件或接口协作，避免 delta-order 与 delta-pay 新增循环依赖。退款超时任务放在 delta-pay，不从 delta-common 反向依赖支付模块。

## 10 验收与上线

以下为开发完成后的验收要求，当前未执行这些新增功能的验收。

| 验收场景 | 必须满足的结果 |
| --- | --- |
| 重复点击或请求重放 | 同一申请只产生一笔有效退款 |
| 换请求编号重复申请 | 不超过可退金额，不并存重复全退 |
| 抢单与超时退款同时发生 | 只允许一个业务结果成功 |
| 指派和自动确认任务并发 | 无法绕过退款冻结及结算限制 |
| 余额入账时数据库异常 | 钱包、流水、退款状态一起回滚 |
| 微信接口超时或回调丢失 | 原单查询恢复，不产生重复退款 |
| 伪造通知或金额不符 | 不改变退款金额和成功状态 |
| 回调与查询同时确认成功 | 只记录一次成功及一次资金变更 |
| 工作进程重启或租约过期 | 任务可以恢复，无重复入账 |
| 后台修改价格或涨价比例 | 退款仍以原支付记录为准 |
| 越权查询或审批 | 用户不能读取他人记录，客服不能超额审批 |
| 历史订单及开关关闭 | 不自动批量退款，已提交任务继续核查 |
| 已结算或已打赏订单 | 按业务边界拦截或转人工处理 |

开发顺序为：先完成数据结构及统一退款服务，再补后台规则和超时任务，随后接入页面、补偿、对账和告警。首期只启用未接单全额退款，第二期再开放部分退款及结算冲正。

上线前备份应用和数据库，执行新增表及兼容字段迁移；新开关默认关闭，历史记录只做明确的退款历史核对和回填，不直接纳入超时退款范围。先在测试环境完成模拟支付和异常测试；正式微信退款联调应在另行授权后进行。

关闭自动退款开关不等于可以直接回退到旧版本。已有在途退款可能只存在于新退款单中，必须保留新执行器和回调处理器，或完成兼容转换后再回退应用。数据库退款记录、占用和流水不得删除；支付和短信开关不因发布该功能而自动开启。

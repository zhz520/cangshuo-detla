# 共享服务组更新入口与发布规则

- 更新时间：2026-11-13（Asia/Shanghai）
- 适用服务组：`delta-shared-prod`
- 适用租户：`jax`、`742`、`747`
- 关联正式版本：客户端 `1.14.10`，授权中心 `0.7.1`

## 1. 唯一正确的结论

JAX、742、747 已经运行在同一个共享后端、MySQL、Redis 和静态制品服务组中。共享组只有一套后端进程，不能由某个租户后台单独安装后端更新，也不存在“三个客户各自点击一次安装”的共享更新流程。

共享组的正式更新路径是：

```text
GitHub 不可变正式制品
  -> 授权中心 delta-shared-prod 服务组计划
  -> cangshuo-shared-release-v1 签名信封
  -> /var/lib/delta-shared/updater/inbox
  -> cangshuo-shared-worker.service
  -> 逐租户备份 -> 校验三个制品 -> Compose 切换 -> 健康检查 -> 审计
```

客户后台“系统更新”页在共享实例上显示“此实例尚未接入更新执行器，请联系维护人员”，这是预期现象。旧 `worker.py` 和 `/api/client/update-plan` 只属于尚未迁移的独立实例，不能用于共享服务组。不要把实例级更新计划交给共享组，也不要把“客户点击安装”写成共享组的发布门禁。

## 2. 两种更新通道

| 项目 | 独立实例更新 | 共享服务组更新（当前 JAX/742/747） |
| --- | --- | --- |
| 适用对象 | 尚未迁入共享组的单客户部署 | `delta-shared-prod` 及其全部启用租户 |
| 授权中心接口 | `/api/client/update-plan` | `/api/service-groups/delta-shared-prod/plans` |
| 签名格式 | 实例更新计划 | `cangshuo-shared-release-v1` |
| 执行器 | `deploy/updater/worker.py` | `deploy/updater/shared_worker.py` / `cangshuo-shared-worker.service` |
| 升级范围 | 一个实例 | 服务组内全部租户共享组件一次性切换 |
| 客户后台按钮 | 客户管理员可选择更新项并点击安装 | 只展示当前版本、最新版本和变更说明；不提供独立安装按钮 |
| 发布方动作 | 发布方准备资产和计划，客户最终点击 | 发布方在维护窗口生成计划、验签、执行和验收 |
| 失败回退 | 恢复该实例组件 | 恢复整个服务组的上一个发布目录、Compose 覆盖和当前版本指针 |

## 3. 共享发布固定流程

1. 从干净工作区构建并上传不可变正式资产，确认 `backend`、`admin`、`h5` 三个 ZIP 的大小和 SHA-256。
2. 授权中心将正式版本同步为 `PUBLISHED`，并确认三个组件都有可校验摘要。
3. 只读核对服务组成员、每个实例的维护期、启用状态和运行时租户编号；三租户集合必须恰好是 `742`、`jax`、`747`。
4. 在授权中心生成服务组计划，填写真实的目标版本、当前版本和维护窗口。计划有效期最多 15 分钟，必须落在服务组允许的维护窗口内。
5. 在生产共享配置下执行 `shared_worker.py validate`，检查签名、服务组、租户集合、`schemaVersion=1`、三个制品摘要、维护窗口和备份要求。
6. 确认 `cangshuo-shared-worker.service` 为运行状态、`allow_execute=true`、`inbox/processing` 为空、没有 `journal.json` 或维护门禁。
7. 将签名信封放入私有 inbox，或由受控执行命令触发同一验签流程。执行器会逐租户备份 MySQL、`upload` 和 `platform` 状态，然后按后端、后台、H5 的顺序切换和健康检查。
8. 验收五个共享容器、六个生产域名、后台和 H5 版本文件、API、静态资源 MIME、三库表数、财务一致性、授权上报和错误日志。
9. 记录计划 ID、服务组、维护窗口、发布目录、备份路径、三制品摘要和审计结果。

## 4. 生产配置和执行边界

- 服务组：`delta-shared-prod`
- 执行器配置：`/www/delta/shared/shared-worker.json`（root-only）
- 租户注册：`/www/delta/shared/tenant-registry.json`（root-only）
- 私有 inbox：`/var/lib/delta-shared/updater/inbox`
- 发布目录：`/www/delta/shared/releases/<plan-id>`
- 当前指针：`/www/delta/shared/current`
- Compose 覆盖：`/www/delta/shared/compose.shared-release.json`
- 备份根目录：`/www/delta/shared/backups`

共享执行器不接受客户端提供的服务器命令、任意路径、容器名、数据库凭据或镜像地址。路径、容器、Compose 文件、备份位置和公钥均来自运维配置。

数据库仍只接受 `schemaVersion=1`。新增字段和表必须由启动兼容检查和独立迁移文件处理；执行器不执行任意数据库迁移。

## 5. 必须保留的证据

每次发布至少记录：

- GitHub Release 标签和发布提交；
- 三个正式资产的字节数和 SHA-256；
- 服务组 ID、计划 ID、当前版本和目标版本；
- 维护窗口和计划生成时间；
- `shared_worker validate` 结果；
- 执行器审计中的 `SUCCEEDED` 或 `ROLLED_BACK`；
- 发布目录、备份目录和恢复结果；
- 五个容器健康状态、六个域名、三库当前表数（1.14.10 为 72 表）、财务 12 项和授权版本；
- 失败原因、回退范围及客户影响。

## 6. 禁止事项

- 不得把共享租户当成三个独立更新执行器。
- 不得用 `/api/client/update-plan` 为共享服务组生成安装计划。
- 不得因为后台显示“尚未接入更新执行器”而安装或启动旧 `worker.py`。
- 不得在一个租户后台只升级共享后端或只替换一个租户的静态文件。
- 不得跳过维护窗口、逐租户备份、摘要校验、健康检查或审计。
- 不得在 `journal.json`、维护门禁或失败回退未处理时继续发布。
- 不得在文档、日志、截图或对话中输出密钥、数据库凭据、完整手机号或客户业务数据。

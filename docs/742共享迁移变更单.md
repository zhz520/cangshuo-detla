## 4. 执行顺序

1. **变更单审批**：记录版本、commit、release manifest SHA-256、维护窗口、负责人和回滚负责人。
2. **最后一次备份**：在停写前完成 MySQL 和文件备份，校验 SHA-256，记录到状态机 `backup_verified` 证据。
3. **进入维护窗口**：停止下单/支付/提现等写入，等待在途任务和聊天排空；确认支付回调接收策略。状态机记录 `maintenance_started`。
4. **导入数据**：把 `client742_game` 导入目标库；核对表数、行数和关键账务表校验和；状态机记录 `data_imported`。
5. **同步文件**：使用 `file_delta.py compare`、`sync --apply`、`verify`；确认 missing/changed 为 0，extra 经确认后保留或另行清理；状态机记录 `files_synced`。
6. **财务对账**：对目标库执行 `financial_reconciliation.py audit --fail-on-violation`；逐笔核对微信账单、退款、提现和结算；状态机记录 `finance_verified`。
7. **切换路由**：切换 742 域名的 Nginx upstream 到共享后端；验证 Host、CORS、WebSocket、静态资源和支付回调；状态机记录 `route_switched`。
8. **业务验收**：客户完成登录、下单、派单、聊天、支付、退款、提现和文件检查；记录客户验收证据，状态机记录 `accepted`。
9. **观察期**：按约定时间观察错误、支付、退款、结算和资源；结束后状态机记录 `observed`。
10. **停旧服务**：确认旧实例无写入后停止 742 旧 Java/MySQL/Redis 运行服务，保留备份；状态机记录 `old_stopped`。

## 5. 回滚

- 路由回滚：把 742 域名 upstream 切回旧后端，验证旧站点和支付回调。
- 程序回滚：恢复旧 Compose/旧 JAR 和 `current.json`，重新健康检查；使用执行器 `recover` 或保留的旧发布目录。
- 数据回滚：只有确认目标库写入无法安全合并时才恢复备份；恢复前停止共享后端写入，恢复后逐笔核对支付/退款/提现。
- 状态机记录 `rolled_back`，证据包含原因、路由代次、回滚验证和保留的备份路径。

# 通知中心与运营后台改版需求整理

整理日期：2026-11-08

## 一、角色定义

本需求涉及四类业务接收人：

| 角色 | 标识 | 主要职责 |
|---|---|---|
| 客户 | `USER` | 下单、查单、申请售后、接收退款结果 |
| 打手 | `PLAYER` | 接收指派、接单、订单状态、审核和提现结果 |
| 客服 | `CS` | 处理订单、审核退款申请、审核打手入驻和主页素材 |
| 超级管理员 | `ADMIN` | 当前系统最高权限账号、最终退款审批、全局数据和安全配置 |

当前系统角色为 `ADMIN`、`CS`、`BOTH`。“超级管理员”直接等同于现有最高权限 `ADMIN`，不再新增独立角色；旧版 `BOTH` 按 `ADMIN` 处理。

## 二、通知中心总体规则

公众号模板通知和短信通知是两套独立通道，但由同一个业务事件触发。每个事件应生成独立的通知任务，并分别记录公众号和短信发送结果。

基础规则：

- 一个业务事件可以通知客户、打手、客服、超级管理员中的多个角色。
- 每个角色使用自己的公众号模板和短信模板，不能继续让四个角色共用同一份内容。
- 同一事件、同一接收人、同一通道只发送一次，避免公众号和接口重试造成重复。
- 公众号需要接收人已完成身份绑定；短信需要有可用手机号。
- 客服上班时才接收订单、人员审核、投诉、退款申请和退款审批类通知；未上班的客服不接收这些通知。
- 超级管理员始终接收运营通知，不受客服上班状态影响。
- 公众号未绑定或短信未配置时不影响订单主流程，只记录失败原因并允许补发。
- 公众号失败最多重试 5 次；短信需要单独配置重试和频控。
- 所有通知记录包含事件编号、订单号、角色、接收人、通道、模板、状态、尝试次数、失败原因和时间。

## 三、通知事件与接收人

### 1. 客户下单及订单状态

| 事件 | 客户 | 打手 | 当班客服 | 超级管理员 |
|---|---:|---:|---:|---:|
| 订单创建但未支付 | 是 | 不广播 | 不通知 | 不通知 |
| 订单支付成功 | 是 | 已指定则通知指定打手；未指定则向在线打手广播 | 是 | 是 |
| 订单指派打手 | 是 | 被指派打手 | 是 | 是 |
| 打手接单 | 是 | 接单打手及协作打手 | 是 | 是 |
| 开始服务/进度更新 | 是 | 订单相关打手 | 是 | 是 |
| 订单完成、待客户确认 | 是 | 订单相关打手 | 是 | 是 |
| 客户确认完成 | 是 | 订单相关打手 | 是 | 是 |
| 订单取消 | 是 | 已指派打手 | 是 | 是 |

有效新订单以支付成功为准。未支付订单只给客户站内提醒，不向客服、打手或超级管理员广播。

未指定打手的已支付订单：

- 向所有在线、状态正常且可接单的打手同时发送公众号和短信通知。
- 如果没有任何在线打手，则向所有正常状态打手发送，并在通知中明确注明“当前暂无打手在线”。
- 已指定打手的订单只通知被指定打手，不向全部打手广播。
- 广播短信按实际接收打手逐人发送，不能依赖聊天群或公共链接。

### 2. 退款与售后

| 事件 | 客户 | 订单相关打手 | 当班客服 | 超级管理员 |
|---|---:|---:|---:|---:|
| 客户申请退款 | 是 | 是 | 是 | 是 |
| 客服完成退款初审 | 是 | 是 | 是 | 是 |
| 客服驳回退款申请 | 是 | 是 | 是 | 是 |
| 超级管理员批准退款 | 是 | 是 | 是 | 是 |
| 超级管理员拒绝退款 | 是 | 是 | 是 | 是 |
| 原路退款处理中 | 是 | 是 | 是 | 是 |
| 退款成功 | 是 | 是 | 是 | 是 |
| 退款失败或被支付渠道退回 | 是 | 是 | 是 | 是 |

退款通知必须携带订单号、退款金额、申请原因、处理结果和下次操作人，不展示完整支付凭据。

### 3. 人员审核

| 事件 | 申请打手 | 当班客服 | 超级管理员（ADMIN） |
|---|---:|---:|---:|
| 打手提交入驻申请 | 是 | 是 | 是 |
| 入驻审核通过 | 是 | 是 | 是 |
| 入驻审核驳回 | 是 | 是 | 是 |
| 打手提交主页素材 | 是 | 是 | 是 |
| 主页素材审核通过 | 是 | 是 | 是 |
| 主页素材审核驳回 | 是 | 是 | 是 |
| 打手因违规被冻结或解冻 | 是 | 是 | 是 |

人员审核通知只发送给当班且具备对应审核权限的客服和超级管理员。未上班客服不接收人员审核通知；没有当班客服时仅通知超级管理员。

## 四、公众号通知配置

后台继续使用「系统管理 → 系统配置 → 公众号通知」。

需要配置：

- 公众号 AppID、AppSecret、网页授权域名和绑定回调页面。
- 客户、打手、管理员、客服四份独立模板组。
- 每份模板组包含订单支付、指派、接单、完成、退款、人员审核等事件映射。
- 每个事件保存微信 `templateId` 与实际字段映射。
- 绑定入口分别位于客户个人中心、打手中心、客服/管理员 H5 工作台。
- 只有已绑定且仍关注公众号的身份可以接收模板消息。

## 五、短信通知配置

后台继续使用「系统配置 → 短信配置」，新增按角色和事件配置短信模板。

需要配置：

- 每个角色的手机号来源：客户手机号、打手手机号、客服/管理员账号手机号。
- 每个事件对应的阿里云短信模板 Code。
- 模板变量，例如订单号、订单状态、退款金额、审核结果、客服姓名、打手姓名。
- 客服上下班状态作为人员审核、投诉、退款和订单短信的发送条件。
- 每日、每小时频控用于防止重复发送；按规定必须广播的全部在线打手不能因条数上限被静默遗漏，需以费用告警和运营监控为主。
- 短信发送失败重试、余额不足告警、模板审核状态检查。

短信模板需要提前在阿里云审核通过，不能直接把公众号模板内容作为任意短信发送。

## 六、客服上班状态与接单通知

新增客服上班开关：

- 客服可在 PC 后台和手机客服端切换“上班/下班”。
- 状态保存到 `staff_shift`，并记录切换时间、IP、设备和操作日志。
- 只有上班客服接收新订单、接单、订单完成、退款申请、投诉、人员审核和退款审批类通知。
- 下班客服不接收上述订单、人员审核、投诉和退款审批类公众号与短信推送。
- 超级管理员不受客服上班状态影响。
- 客服接单或处理退款任务期间，建议禁止直接下班或提示存在未完成任务。
- 长时间无操作可自动下班，自动下班时间需配置。

打手接单通知需要明确展示：

- 客户名称或脱敏后的客户标识
- 订单号与商品名称
- 接单打手名称
- 接单时间
- 是否存在协作打手

示例：`客户“张先生”的订单 #A123 已由打手“北泽”接单，接单时间 14:35。`

## 七、退款审批流程

退款由客服处理和超级管理员终审，客服不能直接完成资金退款。

建议状态：

1. `REFUND_REQUESTED`：客户或客服发起退款申请。
2. `CS_REVIEWING`：客服核对订单、资金和售后证据。
3. `CS_REVIEWED`：客服初审通过，等待超级管理员审批。
4. `SUPER_ADMIN_APPROVING`：超级管理员审批中。
5. `APPROVED`：批准退款，等待调用支付渠道。
6. `PROCESSING`：已向微信支付提交退款。
7. `REFUNDED`：退款成功。
8. `FAILED`：渠道退款失败，需要重试或人工处理。
9. `REJECTED`：客服或超级管理员驳回退款。

强制规则：

- 一张订单同一时间只能有一个进行中的退款流程。
- 客服只能提交初审意见，不能直接调用退款接口。
- 超级管理员批准后才能创建退款任务。
- 退款回调必须验签并按退款单号幂等处理。
- 退款成功后同步冲正待结算收益、已提现余额或退款待追回账款。
- 申请、初审、批准、拒绝、执行和失败都要通知四类相关角色。
- 退款按钮和审批按钮均记录操作人、IP、角色、时间、前后状态和原因。

## 八、数据看板

### 超级管理员数据看板

- 今日访客数、日活用户数、新增用户数
- 今日订单数、有效订单数、成交金额、退款金额
- 今日与昨日、近 7 天、近 30 天对比
- 订单漏斗：访问 → 商品浏览 → 创建订单 → 支付 → 接单 → 完成
- 在线打手、离线打手、冻结打手和当前进行中订单数
- 待派单、待接单、待审核、退款待审批、投诉待处理数量
- 客服上班人数、平均响应时间、处理订单数、退款处理时长
- 可点击统计数字查看明细人员列表和具体订单

### 客服数据看板

- 今日待派单、进行中、待审核、退款申请、投诉数量
- 今日访问、订单、成交额的可查看范围由权限控制
- 在线/离线打手数量及人员明细
- 自己的上班状态、接单量、响应时间、审核积压
- 快速入口：订单、退款、人员审核、素材审核、接力/换人审核

### 数据定义

- 日活用户：一天内至少发生一次有效业务请求的登录用户，按用户 ID 去重。
- 日访问用户量：一天内访问 H5 的独立访客，按匿名访客标识去重。
- 在线打手：打手主动开启接单且心跳未过期。
- 离线打手：未开启接单或心跳超时。
- 有效订单：支付成功且未取消、未退款的订单。
- 数据对比默认使用相同时段，避免今天半天对比昨天全天造成误导。

需要新增访问日志或聚合表，不能仅依赖订单表推算访客；访客标识优先使用匿名 Cookie/设备标识，IP 和 UA 只保存哈希并设置保留期限。

## 九、订单详情与手机号

管理员和客服订单详情增加客户手机号字段：

- 登录后台的管理员和客服直接显示完整手机号，不使用星号脱敏。
- 订单列表、订单详情、退款审核、客户管理、打手管理和客服管理页面中的号码统一显示完整值。
- 客服查看完整客户电话不需要单独授权，也不需要二次验证。
- 仅向当前登录的后台账号返回完整号码；用户端、打手端不得查看其他人的手机号。
- 复制手机号、导出包含手机号的数据必须写操作日志。
- 手机号不进入公众号通知、短信内容、普通日志和公开导出。
- 普通用户和打手不显示其他人的手机号字段。

## 十、接力审核与换人审核合并

新增统一的「履约审核」页面：

- 顶部筛选：全部、接力、换人。
- 列表展示订单号、客户、打手、申请原因、申请时间、超时时间和状态。
- 详情页根据类型加载对应审核材料，不混合业务状态。
- 审核动作统一为通过和驳回，但后端仍调用各自业务校验。
- 批量审核只允许处理满足相同状态和权限的记录。
- 审核结果统一进入操作日志和待办中心。

该合并是页面入口与审核体验合并，不合并底层数据和资金规则，避免改变接力分成和换人状态机。

## 十一、手机端超级管理员与客服后台

参考截图的卡片式移动端布局，保持现有黑白品牌风格。

首屏结构：

1. 顶部待办数据：待派单、进行中、待审核、退款待审批、售后待处理。
2. 今日数据卡：访客数、有效订单、已收款、在线打手。
3. 快捷管理卡：订单、退款、打手、客户、商品、公告。
4. 审核中心卡：人员审核、素材审核、接力/换人。
5. 客服运营卡：上班开关、本班订单、响应时间、未完成事项。
6. 底部导航：工作台、订单、消息、我的。

权限规则：

- 超级管理员看到全局数据、退款终审、配置和财务入口。
- 客服只看到自己权限范围内的订单、客户资料、退款初审、审核和客服状态。
- 无权限的卡片直接隐藏，不展示不可点击的空按钮。
- 手机端支持下拉刷新、骨架屏、分页和失败重试。

## 十二、验收标准

- 客户下单、所有订单状态、退款全程、人员审核和素材审核的事件均生成公众号与短信通知记录。
- 四个角色使用各自模板，任一角色模板为空时只回退旧模板，不影响其他角色。
- 同一事件同一角色同一通道不重复发送。
- 下班客服不收到订单、人员审核、投诉和退款审批通知，超级管理员始终收到。
- 未指定打手的已支付订单向全部在线打手广播；没有在线打手时向全部正常状态打手广播，并显示“当前暂无打手在线”。
- 打手接单通知包含客户标识、接单打手、订单号、商品和接单时间。
- 客服可以初审退款，但无法绕过超级管理员调用退款接口。
- 退款申请、审批、执行、成功和失败均有通知和操作日志。
- 数据看板的在线/离线打手数量与人员明细一致。
- 日活、访客、订单和金额可通过数据库查询复核。
- 管理员和客服在后台查看手机号时直接显示完整号码，不脱敏、不需要额外权限或二次验证；复制和导出仍有审计记录。
- 接力审核和换人审核共享入口，但业务规则和资金计算保持独立。
- PC、手机、微信内置浏览器均可操作，页面无横向溢出和重复提交。

## 十三、建议实施顺序

### 第一阶段：通知与权限基础

- 按现有最高权限 `ADMIN` 作为超级管理员
- 完成客户、打手、管理员、客服四角色公众号模板组
- 完成短信角色与事件模板体系
- 统一业务事件、通知任务、幂等和重试
- 完成客服上班状态及订单通知过滤

### 第二阶段：资金与审核流程

- 退款两级审批流程
- 退款事件通知与资金冲正
- 订单详情及后台列表客户手机号完整展示、权限与审计
- 接力/换人审核合并

### 第三阶段：数据和移动端

- 访问日志和日活数据采集
- 管理员/客服数据看板与人员明细
- 手机端卡片式工作台
- 趋势、漏斗和数据对比

## 十四、已确认规则

1. “超级管理员”等同于当前最高权限 `ADMIN`，不新增独立超级管理员角色。
2. 未指定打手的已支付订单向全部在线、状态正常的打手发送公众号和短信广播。
3. 如果没有任何在线打手，则向全部正常状态打手发送，并在通知中注明“当前暂无打手在线”。
4. 下班客服不接收订单、人员审核、投诉和退款审批类通知；超级管理员始终接收。
5. 客服查看完整客户手机号不需要单独权限，也不需要二次验证。

# Delta 多租户架构改造执行方案

- 文档版本：1.2
- 编写日期：2026-11-10（Asia/Shanghai）
- 源码分析基线：主仓库 1.11.2，提交 053543c38587729bbc53fbc084f6e807971c3903
- 状态：W2 基础能力、W3/W4 数据与缓存隔离、W5 支付配置、W6 聊天/文件/任务、W7 租户授权状态已落地；W1 注册导出和 W9 发布计划验签、执行器、备份/健康检查、Compose 覆盖安装/恢复、失败回退、合成跨版本升级/回退、迁移状态机已验证，W9 的正式发布包和真实客户迁移尚未完成。共享模式默认关闭，当前不可用于生产。

## 1. 目标与适用边界

目标：客户增加时，不再为每个客户重复启动 Java、MySQL、Redis；统一核心代码，降低重复服务的基础内存开销，同时保留各客户的品牌、域名、数据和支付配置。

采用：**共享 Java 后端服务组 + 共享 MySQL 服务、每租户独立数据库 + 共享 Redis + 共享前端静态产物**。授权中心继续独立运行。

本次选择是共享应用方案，不采用“每客户仍运行一套 Java”的方案。暂不把全部客户业务数据合并到同一组带 tenant_id 的表，也不在本次同时拆微服务或引入 Kubernetes。

适用对象：最新源码 cangshuo-detla、授权中心 cangshuo-detla-authorize，以及待逐个迁入的 742、747、delta/JAX。以后客户使用同一开通流程。

本文件仅授权范围内的设计交付。创建文档不等于批准生产迁移、停机、替换线上程序或改变客户安装规则。现有版本、授权、发布规则继续有效，规则冲突按 VIBE_CODING.md 和 development-conventions.md 处理。

### 1.1 完成后应达到的效果

- 新增客户主要增加租户登记、数据库、凭证、域名和配置，不增加整套业务服务。
- 一个功能只在主仓库实现，客户目录不再维护不同版本的业务逻辑。
- 客户继续使用自己的前台域名和后台域名；后台 PC 为 /，工作人员手机版为 /h5。
- 订单、用户、钱包、提现、聊天、文件和商户配置按租户隔离。
- 可单独暂停、备份、导出、迁移一个租户；大客户后续可以迁到专用服务组。
- 节省多少内存，以同等业务负载下的实测为准，不承诺未经测量的节省比例或可承载客户数。

### 1.2 必须接受并处理的代价

| 代价 | 执行要求 |
| --- | --- |
| 共享应用或 MySQL 故障影响多个客户 | 监控、恢复演练、备份，以及后续按服务组分散故障范围 |
| 大客户挤占资源 | 每租户请求、连接、上传、任务并发配额，同时限制系统总量 |
| 多个租户凭证存在于同一服务信任边界 | 最小权限、密钥引用、审计；不能声称独立库等于完全物理隔离 |
| 一个共享进程只能运行一个后端代码版本 | 统一发布；不同版本灰度使用不同服务组和租户路由 |
| 每租户一个库仍有维护成本 | 自动开通、迁移、备份、恢复和版本记录 |

## 3. 目标拓扑与部署方式

~~~mermaid
flowchart TB
    WEB[各客户前台和后台域名] --> EDGE[Nginx：已登记域名映射与 HTTPS]
    EDGE --> STATIC[共享前端静态文件]
    EDGE --> APP[共享 Java 服务组：租户识别、认证、业务]
    APP --> MYSQL[共享 MySQL 服务]
    MYSQL --> A[742 独立数据库]
    MYSQL --> B[747 独立数据库]
    MYSQL --> C[JAX 独立数据库]
    APP --> REDIS[共享 Redis：租户命名空间]
    APP --> FILES[租户文件空间与私密凭证存储]
    AUTH[独立授权中心：客户、权益、许可证、版本] -.签名元数据同步.-> APP
    RELEASE[统一正式制品] --> DEPLOY[受限发布执行器]
    DEPLOY -.按服务组发布.-> APP
~~~

- 第一阶段可采用一个业务 Java 进程、一个 MySQL 服务、一个 Redis 服务及统一静态服务。实例数由测量和可用性要求决定，单实例方案不具备高可用。
- 授权中心继续使用自身存储，不把客户业务库放进授权中心 SQLite。
- 租户运行登记可使用共享 MySQL 中的独立元数据库；独立连接与账号，不作为业务数据源的默认库，不额外引入常驻微服务。
- 注册信息与授权快照受控同步、本地缓存；正常业务请求不逐次调用授权中心。未知或不完整登记拒绝服务，已有许可按当前有效期和维护策略执行。
- 后续增加服务组时，由登记映射决定租户在哪一组；同一租户同时只能有一个明确的活动写入目标。

共享应用配独立数据库是成熟的数据隔离组合，仍需自动化管理数据库并处理共享资源竞争。参见 [Microsoft 多租户数据架构](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)。上述取舍是针对 Delta 的设计，不要求采用 Azure 服务。

## 4. 租户、域名与配置模型

### 4.1 租户的定义

一个独立经营、独立账务的项目/品牌站点为一个租户。关系为：商务客户 → 经营项目/租户 → 部署位置。一个客户可以有多个租户。

tenant_id 使用不可变内部标识。742 等名称仅为可读编号；域名、服务器和品牌变化不能重建租户身份。同手机号在两个租户的账号、角色、余额独立；本期不实现跨客户账号、钱包或打手池共享。

### 4.2 拟新增的登记信息

以下为逻辑模型，待实现时落为可重复迁移及接口，不是已经创建的表。

| 记录 | 最小字段/约束 | 管理边界 |
| --- | --- | --- |
| tenant | tenant_id、customer_id、project_id、状态、配置版本 | 授权中心管理商务关系，运行侧同步必要信息 |
| tenant_domain | 规范化域名、tenant_id、入口类型、归属验证、证书状态 | 域名全局唯一；前台/后台入口类型分别记录 |
| tenant_placement | tenant_id、服务组、db_ref、credential_ref、storage_ref、路由代次 | 仅受限运维操作能改；不能由客户端指定 |
| tenant_license_binding | tenant_id、原 instance_uuid、许可证、协议版本 | 保留旧授权映射，物理容器 ID 不替代租户许可 |
| tenant_schema_history | 租户、迁移编号、校验和、状态、时间、执行批次 | 每库有自身记录；中心汇总状态，不复制业务数据 |
| deployment_group | 服务组、制品摘要、代码版本、数据库兼容区间 | 区分“应用部署版本”和“租户数据库版本” |
| operation_audit | 操作人、租户、动作、结果、关联任务编号 | 不记录凭证、完整证件或业务消息正文 |

凭证字段保存受保护存储引用，不把数据库密码、JWT 密钥、支付私钥写进公开登记接口、Git 或普通日志。运行账号读必要登记；开通/迁移账号具备独立权限且不用于普通请求。

租户状态至少区分：开通中、待迁移、可服务、维护、停用、迁移失败。更新失败只阻止该租户进入新环境，不把整个共享服务误判为全部不可用。

### 4.3 域名与前端

- 老客户保留原域名，实际域名清单在迁移前核对。
- 新客户默认分配平台子域名，并支持绑定自有域名；完成归属验证后才启用，解绑时撤销路由和缓存。
- 同一客户前台、后台域名映射同一 tenant_id，但保留入口类型和角色权限差异。
- Nginx 仅接收登记域名；后端只信任明确配置的反向代理，覆盖不可信的转发头，拒绝未知 Host 和任意 X-Tenant-ID。
- CORS、WebSocket Origin、OAuth 返回地址、支付返回地址按租户和入口白名单校验；不因为共用后端就放开全部来源。
- Web 端使用同源 /api 或受控运行时配置，公共配置接口只返回品牌、入口和公开功能信息，不返回数据库或凭证引用。
- 站点配置、头像、浏览器存储和 Service Worker 缓存需考虑租户与入口；品牌头像遵守上传头像 → 品牌 Logo → 品牌首字。
- 用户前台保持现有业务；工作人员后台 / 与 /h5 保持区分，/mobile 不恢复为业务页面。
- 不同 AppID 的小程序仍可能分别构建和提交。小程序不一定存在网页 Host/Origin，使用登记的实例入口或租户定位信息，并核对 AppID、登录身份及权限；定位参数本身不构成授权。

## 5. 后端必须实现的隔离契约

### 5.1 请求、登录和事务

顺序固定：可信入口解析 → 查询租户登记/状态 → 建立租户上下文 → 验证登录态 → 校验角色、权益与资源归属 → 获取租户数据源 → 开启业务事务 → 执行 → finally 清理上下文。

- 游客请求也必须确定租户；游客查单凭证、验证码和签名 URL 绑定租户。
- JWT/会话包含 tenant_id、用户 ID、角色和凭证版本；服务端核对请求租户与签名身份一致，不能先相信未验签 claim 来决定权限。
- 默认迁移策略为要求用户重新登录，不直接合并旧 Redis 登录态。若需要兼容旧会话，另行实现可审计的租户绑定交换流程并测试。
- 密码与原有加密数据不得因合库而失效。保留各客户 AES/实名等解密材料及版本，通过租户密钥解析器加载，不能改为一个全局 AES_KEY。
- tenant context 不向不相关线程隐式继承。异步执行显式捕获受信任上下文，异常、取消、线程复用均清理；事务内禁止切换租户。
- 不同租户可以存在相同数据库主键。日志、队列、文件、外部关联标识使用包含租户的复合身份；不能凭裸 userId/orderId 定位租户。

### 5.2 数据源与连接池

- MyBatis、JdbcTemplate、原生 JDBC、事务管理器必须使用同一租户路由契约；排查手动新建连接和硬编码库名的路径。
- 每租户数据库使用只允许访问本库的账号。运行账号没有建库、用户管理或全局访问权限；DDL 由受限迁移任务执行。
- 可基于项目兼容版本的 AbstractRoutingDataSource 实现封装；不设置业务默认库，显式拒绝空/未知租户，并关闭宽松回退。仅设置 setLenientFallback(false) 仍不足以阻止 null 回退到已配置默认库，必须测试全部路径。参考 [Spring 6.2 数据源路由 API](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/jdbc/datasource/lookup/AbstractRoutingDataSource.html)。不因此升级 Spring 主版本。
- 连接池按需创建，空闲回收；配置总连接预算、单租户上限、等待超时及活跃池数量上限。回收与凭证轮换要等待在用连接释放，不向其他租户复用带旧身份的连接。
- 总预算覆盖所有应用副本、灰度实例、迁移、备份和运维连接，不能只核对单个 JVM。
- 租户配置刷新采用完整版本校验和原子替换；数据源故障时返回该租户不可用，禁止尝试其他租户数据库。

### 5.3 Redis、内存缓存和锁

- 统一格式：delta:{tenant_id}:业务类型:业务键；集群哈希标签如需采用，在实现时单独验证槽位分布，不能把示例直接当作扩展策略。
- 覆盖登录态、配置、验证码、短信限流、幂等键、分布式锁、公众号票据、在线状态、统计、Pub/Sub 频道以及本地 Map 缓存。
- 建立统一 TenantRedis/CacheKey 门面，限制业务直接访问原始客户端；共享进程中的缓存按租户设容量、TTL 和清理机制。
- Redis 不直接暴露客户。应用角色使用 ACL 限制命令和键/频道范围，不开放 FLUSHALL、CONFIG、任意脚本管理等危险能力；命名空间和不同逻辑库本身不是安全隔离。参见 [Redis ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)。
- Redis 不是订单、余额和退款的最终事实来源；关键状态持久化到租户 MySQL，资金并发仍用事务、唯一约束和行锁。
- 明确共享缓存的内存上限和逐出策略；会话丢失要求重新登录，关键幂等不能仅依赖可能被逐出的缓存。Redis 故障时限流和关键操作采用已测试的拒绝/降级策略。

### 5.4 支付、退款、通知

- 微信支付、公众号、小程序、短信、邮件客户端按 tenant_id + 配置版本缓存，设容量上限，不继续使用单客户全局对象。
- 回调先通过已登记入口定位候选租户，再用该租户凭证验签和解密，校验商户号、AppID、金额、交易号、本地支付单及业务类型；回调中的租户参数不是可信授权。
- 无法定位或验签失败直接拒绝，不遍历全部客户凭证尝试解密，也不默认为第一个商户。
- 幂等持久化在对应客户库；同租户重复回调只处理一次，不同租户相同业务编号互不影响。若多个租户共用同一商户号，外部交易编号还需满足该商户范围唯一性；旧交易编号保持原样。
- 旧订单退款和延迟回调需要原支付配置/证书版本，轮换凭证时保留安全的历史解析策略。
- 维护、迁移、授权到期后的在途支付/退款按既定业务策略处理，禁止误停全部回调或把其他客户也停用。
- 授权中心销售功能的收款配置与客户业务商户配置继续分离。

### 5.5 聊天、文件、后台任务

- WebSocket 握手和首次认证绑定租户；连接键为租户 + 角色 + 用户 ID，每条消息校验会话归属。管理员广播只在本租户生效。
- 单 JVM 可保留本地连接管理；在启用多个应用副本前实现跨节点投递、离线补拉、去重与重连。粘性会话不能保证收发双方位于同一节点。
- 文件根目录由可信 storage_ref 决定；验证规范化路径和文件归属。公开商品图片/Logo 与私密聊天附件、实名材料、支付证书分开管理。
- 公开资源缓存键包含域名或租户路径；私密文件通过鉴权读取/短期授权，不允许 Nginx 把整个租户根目录公开。旧文件 URL 通过明确映射兼容。
- 定时任务改为按可服务租户分页调度，使用有限线程池、超时和每租户并发上限；失败租户不阻塞其他租户。
- 锁键、队列消息、重试和死信记录带 tenant_id；从可信任务登记恢复上下文，不直接信任任意消息字段。
- 多副本和迁移期间采用单租户任务所有权及 fencing 代次控制，防止旧任务在锁失效后继续写入；关键结果以数据库幂等约束保证。
- 批量导出、图片解码、数据统计和备份也受配额控制，避免一个客户占满全部工作线程。

## 6. 代码改造清单与工作包

以下新增名称是拟定职责，不代表文件已经存在。先沿用现有模块化单体，避免新模块产生循环依赖。

| 编号 | 范围/入口 | 交付内容 | 前置依赖 | 完成标准 |
| --- | --- | --- | --- | --- |
| W0 | 生产只读盘点、部署资料 | 资源基线、客户差异、数据与回调清单 | 无 | 每个客户有可核验记录，不含秘密 |
| W1 | 授权中心 server/store.mjs、management.mjs、http.mjs；运行登记 | 租户/域名/部署映射、受限开通接口、审计 | W0 | 开通幂等、域名冲突拒绝、控制面故障策略验证 |
| W2 | delta-common 租户基础；SecurityConfig、JwtAuthenticationFilter、TokenService | TenantContext、入口解析、租户身份与会话、密钥解析 | W1 | 空租户、伪造入口、跨租户 Token 均拒绝 |

## 8. 内存、连接与容量验收

### 8.1 先测量，后设置预算

在代表性低峰和业务高峰分别采集：宿主机可用内存/Swap、各容器 RSS/工作集、JVM 堆和非堆/GC、MySQL 缓冲池与连接数、Redis 使用量/逐出数、请求量及 p95/p99 延迟、WebSocket 连接、任务积压、文件 I/O。记录业务负载和采样时间，不能只比较空闲瞬时值。

预算满足：所有进程与容器峰值预算 + 文件缓存和系统开销 + 发布/迁移余量 ≤ 主机可用容量。JVM 的 Xmx 只限制堆，不等于进程全部内存。

数据库连接预算满足：所有服务组和副本的活跃租户连接池上限总和 + 登记库 + 任务/迁移/备份/运维连接 + 安全余量 ≤ 实测可承受连接数及 MySQL 配置上限。

本机已内存紧张时，试点灰度需评估旧服务、新服务、数据导入和备份并存的临时峰值；余量不足，使用临时隔离测试/迁移资源或明确维护窗口，不直接在满载服务器同时启动新旧全套系统。

### 8.2 P0 必须填写的验收表

| 指标 | 现状实测 | 目标/允许阈值 | 验证方式 |
| --- | --- | --- | --- |
| 主机容量、峰值工作集、可用余量 | 待采集 | 待测算 | 同等业务负载的迁移前后对比 |
| 目标客户数及并发活跃租户数 | 待确认 | 待确认 | 活跃与休眠租户混合压测 |
| 请求 p95/p99、错误率、数据库等待 | 待采集 | P0 固定阈值 | 正常峰值与单租户突发场景 |
| 总连接上限、每租户连接/任务配额 | 待采集 | 待测算 | 多副本、灰度和迁移并存测试 |
| 服务恢复时间 RTO、允许数据损失窗口 RPO | 待确认 | 业务确认后固定 | 从备份/日志实际恢复并对账 |
| 试点观察期、维护窗口、容量余量 | 待确认 | 变更单固定 | 覆盖高峰、支付退款和结算周期 |

任何跨租户数据访问、错商户、重复入账、未解释资金差异的容忍度为零。其它阈值未填完前不能宣称性能验收通过。根据实测决定拆服务组或独立数据库服务，不无限增大 JVM 堆或数据库连接数。

## 9. 数据库演进与共享发布

### 9.1 迁移机制

- 每个租户库保留迁移编号、校验和、开始/结束时间和结果；同一迁移重试不会重复改写数据。先在实际 MySQL 版本上验证，H2 不能替代。
- 把现有初始化 SQL、两套迁移目录和 DatabaseCompatibility 的行为整理为有序迁移清单；不能只导入基础 delta_game.sql。
- 先兼容扩展，后切换代码，最后在另一期清理旧结构。涉及账务数据改写必须有对账和恢复设计。
- 在共享模式下，由显式迁移任务使用短期受限权限执行 DDL；应用启动只验证就绪库，不让每个 JVM 启动都扫描并修改全部租户库。
- 每库迁移互斥、系统限制并发。失败记录可定位并重试；不就绪租户保持旧服务或维护态，其他已验证租户照常服务。
- 制品记录支持的数据库结构区间；路由前核对租户库版本。数据库版本、产品版本、许可协议版本、部署计划版本分别记录，不能混为一个 schemaVersion。

### 9.2 新旧更新模式共存

现行规则要求客户在后台最终点击安装。拟议共享模式要求由平台按服务组发布，客户不能触发共享 JVM 更新。**这项规则变更尚待用户确认，本文不将其视为已批准。**

- 尚未迁移的独立客户继续原更新流程，助手不代点击。
- 共享租户页面展示当前服务版本、变更说明和租户功能状态；功能开关不是独立安装后端版本。
- 新发布计划应绑定目标环境、服务组、制品摘要、数据库兼容条件和执行身份；沿用不可变正式制品、摘要校验、审计和健康检查原则。
- 现有 worker 的单实例签名计划不能直接用于共享服务组。新增协议及执行器行为需要测试、兼容策略和独立审查，不通过放宽旧校验绕过限制。
- 授权中心保存权限与发布元数据，不获得任意服务器命令执行权；实际操作由只接受固定动作和受信任目标的执行器完成。
- 新旧版本灰度使用不同服务组，将完整租户路由到一个版本；不能对同一租户随机分发到结构不兼容的版本。
- 正式版本按实际兼容性决定；若引入不兼容授权/更新协议或整体迁移，按主版本规则处理。本文不提前修改 1.11.2、重打标签或创建正式 Release。

## 10. 逐客户迁移操作流程

### 10.1 准备与演练

1. 确认唯一目标租户、旧实例 UUID、域名、真实版本、业务负责人、维护窗口及恢复负责人，形成变更单。
2. 备份该客户 MySQL、uploads、环境配置、许可证/实例状态、各类加密密钥和支付历史凭证；保留原访问权限并加密保存。禁止把 A 客户数据放入 B 客户环境。
3. 在隔离环境恢复该客户自己的备份，禁用生产支付、短信、邮件、公众号发送和生产定时任务；验证完整表结构、密文解密、文件路径及历史支付退款解析。
4. 建立租户登记、独立目标数据库账号和存储空间，导入初始数据并演练迁移。保留业务主键，不把多客户数据混表重编号。
5. 对比所有业务表记录量、关键索引/唯一约束、逐账户余额/冻结金额/待结算、支付/退款/提现累计值、订单状态和文件清单；总金额一致不能代替逐账户核对。
6. 验证旧 URL、支付回调、OAuth、公众号与小程序入口。保持域名时优先切换内部路由，减少 DNS 传播期间的双入口问题。

### 10.2 正式切换：确保只有一个写入方

建议首批采用短维护窗口的单写入方切换，不在首批实现业务双写。该方式仍需处理支付回调和正在执行的任务，不能仅关闭网页按钮。

| 顺序 | 操作 | 放行证据 |
| --- | --- | --- |
| 1 | 租户进入维护，阻止新订单及普通写操作；暂停旧定时任务、消费者和旧更新器任务 | 已确认受控入口和后台写路径均停止接收新任务 |
| 2 | 排空在途请求/事务，关闭或排空 WebSocket 写入，确定旧写入方被隔离 | 旧任务停止、连接/事务检查、路由与任务代次记录 |
| 3 | 切换支付/退款回调到已验证的维护接收策略 | 不会丢失已确认回调或写入错误数据库 |
| 4 | 进行最终一致性导出与文件增量同步；旧库停止业务写入 | 备份完成，快照边界明确，文件与库可对应 |
| 5 | 导入/迁移目标库并执行对账，核对凭证和文件引用 | 无未解释差异，目标结构与代码兼容 |
| 6 | 原子切换该租户业务及回调路由，使用新的路由代次；旧实例不得写新库或旧业务库 | 只有目标服务拥有活动写入权 |
| 7 | 恢复回调处理，核对在途支付并恢复任务，完成受控业务验证 | 回调和补偿幂等、任务不重复、资金核对正确 |
| 8 | 开放租户普通写入，强制旧登录态重新登录，进入观察期 | 主要业务链路、错误率、内存、连接和对账正常 |

回调维护策略必须在演练时选定并实现：优先使用已验签、可持久化且可幂等重放的受限接收通道；只有持久化成功才能确认接收，敏感报文加密保存。若暂不具备该能力，维护期间按支付协议明确返回失败，让支付平台重试，并在切换后主动查单/退款查询对账；不得返回成功后丢弃报文，也不得只依赖无限重试。允许窗口与补偿方式必须验证。

进入步骤 4 后旧业务库不得继续接收回调写入。单纯 DNS 切换不能保证这一点；需同时控制旧服务、直连地址、任务和回调入口。若无法证明单写入方，不继续切换。

### 10.3 观察与旧环境处置

- 观察期长度写入变更单，覆盖业务高峰、延迟回调、退款、结算和通知任务；出现隔离或资金问题立即停止扩大迁移。
- 验收后停止该客户旧 Java、MySQL、Redis 运行服务以释放内存，但保留可恢复的配置、镜像/制品和数据备份。
- 不把“暂时没报错”作为删除旧数据的依据；备份保留和删除按已确认期限执行。本文不授权删除旧实例数据。
- 同一服务器无法容纳迁移峰值时，先调整执行顺序或使用临时资源，不能边导入边让旧实例失控写入。

## 11. 回退与事故处理

| 时点/故障 | 允许的动作 | 禁止做法 |
| --- | --- | --- |
| 尚未切换且目标未承接新业务 | 停止迁移，恢复旧路由和旧写入权，处理维护期间积压回调 | 新旧两边同时恢复写入 |
| 已切换但新版本程序异常 | 暂停目标租户写入；在当前最新数据库上运行已验证兼容的旧程序版本 | 直接恢复迁移前数据库覆盖已确认交易 |
| 新库已产生支付、退款、订单或文件 | 先保留最新状态，执行查单、对账和修复；必要时设计反向迁移 | 只把域名切回旧库，丢掉新增账务 |
| 数据不兼容旧代码 | 维持维护状态，优先前向修复或专门反向迁移；审批后执行 | 声称换回旧 JAR 就完成恢复 |
| 单租户迁移失败 | 仅隔离该租户；其他租户保持原服务 | 回滚整个共享 MySQL 或全量清空 Redis |
| 共享基础设施故障 | 按恢复方案重建，并按租户核对数据、回调与任务 | 恢复成功前继续接受不可持久化的资金操作 |

恢复完成要核对应用版本、数据库结构、路由代次、任务所有权、授权状态、文件引用、资金流水和支付平台交易结果，保存完整事件记录。已有付款不能通过简单“数据库回滚”撤销。

# 沧烁电竞系统研发约定

在线版本：https://cangshuo-development-conventions.knobbycity.chatgpt.site

- 版本：1.8
- 生效日期：2026-11-21
- 适用范围：沧烁电竞客户端、授权运营中心、部署执行器及相关后台、H5、小程序和接口。

## 1. 基本原则

1. 先确认业务边界，再改代码。涉及权限、金额、授权、数据库和更新协议的需求，必须先梳理状态流和数据影响。
2. 同一批开发、调试和验收中的问题合并发布，不为每一个小修复单独增加版本号。
3. 所有正式发布必须可追溯到 Git 提交、构建产物、SHA-256 摘要和更新项配置。
4. 客户业务数据、上传文件、支付配置和授权私钥不得进入代码仓库、普通日志或公开文档。
5. 发布前必须完成自动测试、构建、制品校验和关键链路验证；高风险功能需要生产灰度或模拟验证。

## 2. 仓库与职责

| 仓库 | 职责 | 默认分支 |
| --- | --- | --- |
| `zhz520/cangshuo-detla` | 电竞客户端后端、管理后台、H5、小程序、更新执行器 | `main` |
| `zhz520/cangshuo-detla-authorize` | 授权运营中心、版本目录、授权签发和更新计划 | `main` |
| 其他客户站点仓库 | 独立客户项目，不复制其他客户的运营数据 | 按项目定义 |

日常修改使用 `codex/<功能简述>` 分支；禁止直接在 `main` 编写未经验证的功能代码。合并前必须同步最新主分支并解决冲突。

## 3. 版本号约定

正式版本统一使用 `MAJOR.MINOR.PATCH`。

| 段位 | 使用条件 | 示例 |
| --- | --- | --- |
| `MAJOR` | 不兼容变更、授权或更新协议不兼容、需要整体迁移 | `2.0.0` |
| `MINOR` | 新增完整业务能力或一组明显可见的功能 | `1.7.0` |
| `PATCH` | 正式版发布后的缺陷、安全或线上阻塞修复 | `1.6.1` |

补充规则：

- 新功能和常规缺陷修复必须在同一验收批次内合并后发布，不能开发一项就升一次版本。
- 当前共享组正式基线为 `1.18.4`；后续常规缺陷/安全修复从 `1.18.5` 起，新功能批次使用 `1.19.0`。520 演示线与共享组生产线分开发布。
- 预览版使用 `x.y.z-preview.N`，预览版不能进入客户正式更新目录。
- 正式标签一经发布不可改写、移动或复用；需要修复时发布新补丁版本。
- 后端、管理后台、H5、小程序版本必须保持一致；更新执行器按三个可部署组件的最低版本判断当前版本。
- 当前已发布历史保留到回滚目的为主，不鼓励继续在旧补丁线上叠加小修复。下一组新增功能应以最新正式补丁为基线并升为 `MINOR`。

版本升级清单：

- 后端平台目录版本号。
- 管理端与 H5 的 `package.json`、锁文件版本号。
- 小程序 `manifest.json` 的版本名和版本码。
- 客户端集成文档或发布说明中的当前版本。
- GitHub 标签、Release 标题和更新项配置。

## 4. 分支、提交和合并

### 分支

- 功能分支：`codex/<功能简述>`。
- 紧急修复分支：`codex/hotfix-<问题简述>`。
- `main` 始终保持可构建、可发布状态。

### 提交

提交信息使用 `type: summary`：

- `feat:` 新功能。
- `fix:` 缺陷修复。
- `security:` 安全修复。
- `refactor:` 不改变行为的重构。
- `test:` 测试补充。
- `docs:` 文档更新。
- `release:` 版本和发布资料。

每个提交只处理一个主题。不得提交密码、私钥、JWT、GitHub Token、微信支付密钥、数据库凭据、客户真实数据和本地运行缓存。

### 合并

合并前必须具备：

- 需求已验证，异常路径和权限路径明确。
- 自动测试通过。
- 构建通过。
- 数据库变更可重复执行或具备明确迁移步骤。
- 没有未推送的正式发布资产。
- 文档和后台配置说明同步完成。

## 5. 接口与安全约定

- 客户 H5 只承载客户和打手业务；管理员、客服的登录、移动工作台和公众号绑定必须使用后台域名，不得重新加入客户 H5 的隐藏入口。后台 PC 入口为 `/`，后台手机入口固定为 `/h5`；`/mobile` 已移除，仅保留静态兼容分流，旧公众号回调配置自动迁移，客户 H5 旧地址只能做显式兼容跳转。
- 后端权限必须独立校验，不能只依赖前端隐藏按钮。
- 用户身份、游客身份、客服、管理员和打手必须使用最小权限。
- 游客接口只能访问本人订单、聊天、投诉、支付和必要的文件上传。
- 订单、聊天、投诉和支付接口必须校验资源归属。
- 金额、支付状态、退款状态和授权状态以服务端数据为准，不信任客户端参数。
- 管理端敏感操作必须校验具体权限，并写入操作日志。
- 私钥只保存在服务器受保护目录；客户端只持有公钥。
- 生产授权中心地址必须使用 HTTPS；HTTP 只允许本机测试。
- 手机号、证件等敏感信息必须脱敏返回；完整联系方式只向管理员、客服及其明确授权人员开放。
- 日志不得记录密码、授权码、JWT、支付密钥、完整证件信息或游客查单凭证。

## 6. 数据库变更

- 新版本涉及表结构时，必须同时维护启动兼容逻辑和独立迁移文件。
- 默认采用新增表、新增可空列或带安全默认值的加列，不删除字段、不覆盖历史业务数据。
- 迁移脚本必须可以重复执行；关键新增列使用 `information_schema` 判断。
- 升级前备份数据库、上传文件、环境文件和实例配置。
- 数据库 `schemaVersion` 必须与更新协议一致；没有回退方案的破坏性迁移不得直接发布。
- 涉及金额、订单状态、退款、结算和授权的 SQL 必须有回归测试。
- 所有手工 `mysql` 命令必须显式使用 `--default-character-set=utf8mb4`，或在会话开始时执行 `SET NAMES utf8mb4`；不能依赖容器内客户端的默认字符集。
- 脚本中写入中文配置、名称、备注和分组时，优先走应用接口；必须直接写 SQL 时使用 UTF-8 文件并回读 `HEX()` 校验，禁止把中文经未声明字符集的 shell 管道传入。
- 2026-11-11 的 742/747 `sys_config` 乱码就是 MySQL 客户端按 latin1 解释 UTF-8 造成的双重编码；后端 `SysConfigController` 会在读取配置时修复已知形态的元数据乱码，但自动修复不能替代正确的写入方式。

## 7. 支付、退款与授权

- 支付回调必须验证签名、商户号、AppID、金额、交易号和本地支付单。
- 余额支付、微信支付、H5 支付、公众号支付和小程序支付分别受独立开关控制。
- 客户业务支付与功能商城授权支付必须使用不同收款主体和配置来源。
- 订单支付成功后只允许一次有效入账，重复回调必须幂等。
- 退款必须记录累计退款金额、退款单号、处理状态和对应订单、用户及操作者。
- 授权只由授权中心签发；客户端不能自行延长维护期或生成上线授权。
- 授权中心不可用时，已有授权保持本地签名校验；是否暂停业务按项目维护策略执行。

## 8. 更新与发布链路

正式发布链路固定为：

1. 开发完成并通过验收。
2. 同步版本文件并生成发布说明。
3. 从干净工作区构建后端、管理端和 H5。
4. 运行 `deploy/qa/check_static_assets.py`，确认后台/H5 构建产物中的所有 `assets/`、`static/` 引用均存在；打包三个组件 ZIP，并生成 `release-manifest.json`。
5. 确认包内版本、Git 提交和 SHA-256；手工解压时必须使用 Python `zipfile` 或等效 UTF-8 解压，并用 `--archive` 校验实际目录与 ZIP 逐文件一致。
6. 创建 GitHub 正式标签和 Release，上传全部资产。
7. 授权中心同步版本并登记必要更新项。
8. 验证维护期、组件资产、摘要和更新计划。独立实例使用实例更新计划；JAX、742、747 使用 `delta-shared-prod` 服务组计划。
9. 独立实例通知客户自行在后台检查并安装更新；共享服务组由发布方在维护窗口执行服务组计划，客户后台不提供共享后端独立安装按钮。
10. 记录发布版本、提交号、资产摘要、计划 ID、审计结果和验证结果。

共享服务组发布还必须遵守：

- 只使用 `cangshuo-shared-release-v1` 签名计划，不得把 `/api/client/update-plan` 的实例计划交给共享执行器。
- 只使用 `cangshuo-shared-worker.service`，不得启动或复用旧 `worker.py`。
- 客户后台显示“此实例尚未接入更新执行器”是共享实例的预期提示，不是故障；系统更新页只展示版本和变更说明。
- 执行前必须确认服务组成员、租户集合、维护窗口、`schemaVersion=1`、三个制品摘要、`allow_execute=true`、无 `journal.json` 和无维护门禁。
- 执行器必须先逐租户备份 MySQL、上传文件和平台状态，再按后端、后台、H5 顺序健康检查；失败回退整个服务组。
- 详细步骤和证据要求见 `docs/共享服务组更新入口与发布规则.md`。

发布禁止项：

- 不使用预览标签替代正式版。
- 不使用旧构建产物冒充新版本。
- 不在脏工作区打包正式资产。
- 不在每次 CI 推送中上传后端、后台或 H5 构建附件；这些大文件会耗尽 GitHub Actions 存储配额。正式制品必须通过发布脚本打包并作为 GitHub Release 资产交付。
- 不让客户直接依赖私有 GitHub 链接下载更新。
- 不在组件缺少 SHA-256 digest 时开放安装。
- 不把“总体版本号”作为部分组件已更新的证据。

## 9. 测试矩阵

| 层级 | 必测内容 |
| --- | --- |
| 后端 | 单元测试、权限、状态流、并发、事务、数据库兼容 |
| H5 | 登录与游客切换、支付、订单、聊天、响应式页面、401 恢复 |
| 小程序 | 登录、支付、返回路径、平台差异、缓存 |
| 管理端 | 权限菜单、配置保存、订单操作、更新任务、操作日志 |
| 静态制品 | 所有 JS/CSS/图标引用存在，HTTP 返回正确 MIME；ZIP 解压后的中文/非 ASCII 文件名与归档一致 |
| 授权中心 | 登录、CSRF、版本同步、更新计划、制品下载、邮件通知 |
| 更新执行器 | 签名、摘要、组件版本、备份、健康检查、回滚、中断恢复 |
| 安全 | 越权、对象归属、开放重定向、SSRF、XSS、上传、限流、敏感信息 |

正式发布的最低自动验证：

- 后端全量测试通过。
- H5 单测和正式构建通过。
- 管理端单测和正式构建通过。
- 更新执行器测试通过。
- 授权中心相关测试通过。
- 三个正式资产均可下载且摘要匹配。

## 10. 发布门禁

只有同时满足以下条件才能创建正式标签：

- [ ] 需求范围已确认，没有未完成的关键路径。
- [ ] 代码已合并到 `main`，工作区干净。
- [ ] 自动测试、构建和发布包校验通过。
- [ ] 数据库迁移和回退说明完成。
- [ ] 权限、支付、授权和更新逻辑复核完成。
- [ ] 后台配置项和用户操作说明已准备。
- [ ] 版本号符合本约定，没有为同一批次反复递增。
- [ ] Release 资产完整且具有 SHA-256 digest。
- [ ] 独立实例已生成可用实例更新计划；共享服务组已生成服务组签名计划并通过 `shared_worker.py validate`，三个制品摘要匹配。
- [ ] 发布记录已保存，客户通知内容已准备。

## 11. 部署与回滚

- 部署前确认目标环境、域名、端口、时区和持久化目录。
- 服务器反向代理必须保留真实 Host 和 `X-Forwarded-Proto`。
- 更新器必须在维护期内执行，并先备份数据库、环境文件、上传目录和实例配置；共享执行器还必须逐租户备份并保留服务组级回退目录。
- 前端更新后必须验证 `/cangshuo-version.json` 的组件与版本。
- 健康检查失败自动回滚；回滚失败时保持维护状态，禁止继续对客户开放写入。
- 回滚必须恢复组件版本和安装计划标记，不能出现“程序已回滚但后台显示已安装”。
- 更新器超过心跳时限时，管理端不得继续提交新任务。

## 12. 事故处理

1. 先停止扩大影响：暂停相关功能或进入维护状态。
2. 保留日志、支付单、订单和授权记录，不覆盖现场。
3. 确认影响范围：客户、订单、金额、授权或数据。
4. 优先回退到最近可验证版本，再处理数据补偿。
5. 恢复后验证登录、订单、支付、退款、聊天和授权。
6. 记录根因、时间线、影响、修复和防复发措施。

## 13. 文档约定

- 功能说明必须包含入口、权限、状态变化、失败提示和后台配置。
- 发布说明必须写用户可见变化，不直接暴露 GitHub 私有链接。
- 数据迁移、支付、授权和更新协议必须单独形成开发文档。
- 文档中的示例不得包含真实密码、Token、证书、客户手机号或生产服务器凭据。
- 文档更新与代码发布同批提交。

## 14. 完成定义

一个任务只有同时具备以下结果才算完成：

- 需求行为已实现。
- 关键异常和权限路径已验证。
- 测试和构建结果可复现。
- 后台配置、用户提示和运维说明完整。
- 版本、发布资产和授权中心状态一致。
- 已提交、已推送，并明确标记是功能分支还是正式发布。

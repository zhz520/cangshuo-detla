## 3. 742 升级记录

742 已于 2026-11-11 完成 `1.11.2 → 1.12.2` 更新。以下保留升级前事实、执行顺序和验收要点；实际结果见 `docs/742-1.12.2升级记录.md`。

### 3.1 已确认事实

- 升级前为独立实例 1.11.2，`schemaVersion=1`，数据库 `client742_game` 已有 65 张表。
- 管理后台、H5、后端、MySQL、Redis 和授权上报均在运行；自助更新器 `cangshuo-updater-742.service` 为 enabled/active。
- 1.11.2 → 1.12.2 没有新的数据库结构版本变化，主要更新为参数校验、静态资源门禁和前端加载修复。
- 1.12.2 不启用共享多租户模式，`tenant.enabled=false` 的默认单租户路径保持不变。

### 3.2 前置事项

- 客户确认维护窗口和短暂停机。执行器会依次切换后端、管理后台和 H5，并做健康检查。
- 更新前重新备份数据库、uploads、platform 状态、`.env` 和 Compose 配置；不能依赖较早的更新备份。
- 资金异常需要单独处理：一笔退款自 2026-11-10 起停在 `REFUNDING`，微信返回 `403 NOT_ENOUGH`；另有 12 笔历史 `PAYING` 待逐笔核对。它们是现有业务问题，1.12.2 不会自动修复，也不是共享迁移的前置替代项。
- 更新窗口内不要同时切共享服务组、修改域名、调整支付回调或迁移数据库。

### 3.3 操作顺序

1. 客户在维护窗口进入后台“系统更新”。
2. 选择 `1.12.2` 的后端、管理后台和 H5 三个必选更新项。
3. 客户点击“安装所选内容”。
4. 执行器验签、校验摘要、备份、切换组件并做健康检查。
5. 按本文第 6 节验收，观察错误、支付/退款、文件、登录和授权上报。

742 本次升级保持在独立实例内完成。共享迁移仍是 NO-GO，详细阻断项见 `docs/742共享迁移变更单.md`。

## 4. 747 升级记录

- 支付、退款、短信、公众号和邮件开关当前关闭；本次不启用这些外部通道。

### 4.2 推荐路径

1. 客户确认维护窗口、短暂停机、数据状态和验收人；确认没有未导出的真实业务。
2. 停写并重新备份数据库、uploads、private、platform、`.env`、Compose、Nginx 和当前 1.5.15 发布目录。
3. 客户在后台先安装 `1.11.2` 的三个必选组件。
4. 验收 65 张表、三组件版本、管理员记录、商品/分类、后台 `/h5`、H5、API、静态资源和授权上报。

不建议从 1.5.15 一步选择 1.12.2。技术上可以生成签名计划，但会把数据库补齐、1.12.x 功能批次和共享运行时变量放在一次切换中，增加定位和回滚难度。

## 5. 备份与回滚

每个客户在更新前都必须重新生成当前快照，至少包括：

- MySQL 全库备份并验证可恢复；
- `runtime/uploads`、`runtime/private`、`runtime/platform`；
- `.env`、Compose 覆盖文件、Nginx 配置和当前发布目录；
- 记录备份大小和 SHA-256，访问权限保持 root-only。

程序回滚优先恢复上一发布目录和 `compose.self-update.json`，按 backend → admin → h5 启动并做健康检查。数据库变更为加法时，旧版本通常仍可启动；如果已产生新版本写入，必须先评估兼容性，再决定是否恢复数据库。不要删除 `runtime/platform/state.json`、授权文件、支付证书或旧发布目录。

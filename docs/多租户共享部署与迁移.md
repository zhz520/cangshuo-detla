# Delta 多租户共享部署与迁移

- 版本：1.2
- 日期：2026-11-11
- 状态：JAX + 742 已在生产共享服务组运行 1.12.3；五个共享容器均已启用健康检查；742 的退款/PAYING 遗留仍待处理。

## 1. 共享部署边界

`deploy/baota/docker-compose.shared.yml` 是共享服务组模板：一个 Java 后端、一个 MySQL 服务、一个 Redis、共享 admin/H5 静态容器。每个租户在 MySQL 中使用独立数据库和独立数据库账号，文件使用 `upload/<tenant>/`，授权状态使用 `platform/tenants/<tenant>/`。

租户注册文件 `tenant-registry.json` 包含数据库凭据和小程序密钥，必须放在只允许运维账号读取的目录，权限建议 `600`，不能进入 Git、聊天、日志或前端。

示例见 `deploy/baota/tenant-registry.example.json`。新增租户时，先创建数据库和账号，再更新注册文件；应用启动时会校验域名唯一、启用租户必须配置域名、数据库和平台客户编号。

上线前可用 `python deploy/updater/shared_registry.py validate <registry.json>` 做纯本地校验；`redact` 输出脱敏副本，`sql --tenant <id>` 生成数据库/账号开通 SQL 模板。该工具不会连接或修改数据库，也不会替代备份、导入和对账。

## 2. 配置要点

`deploy/baota/.env.shared.example` 提供共享组环境变量模板。关键项：

- `TENANT_MODE_ENABLED=true`：启用共享租户模式和 Host 路由。
- `TENANT_REGISTRY_FILE`：注册文件路径，文件必须在容器内有只读挂载。
- `FILE_UPLOAD_PATH`：共享上传根目录；公开文件实际路径是 `upload/<tenant>/yyyy/MM/dd/`。
- `PLATFORM_STATE_PATH`：共享实例状态基准路径；实际按租户写入 `tenants/<tenant>/state.json`。
- `PLATFORM_CUSTOMER_ID`：单租户兼容默认值；共享租户应由注册文件中的 `platformCustomerId` 覆盖。
- `PLATFORM_REPORT_URL`、`PLATFORM_PUBLIC_KEY_PATH`：授权中心同步端点和验证公钥。

管理端和 H5 前端仍然分别使用共享 `admin`、`h5` 容器；宿主机 Nginx 将每个客户的后台域名和用户域名分别转发到这两个容器。后台 PC 是 `/`，工作人员手机版是 `/h5`。

## 3. 数据库开通

每个租户至少需要：

```sql
CREATE DATABASE delta_tenant_a CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
CREATE USER 'delta_tenant_a'@'%' IDENTIFIED BY '<random-password>';
GRANT ALL PRIVILEGES ON delta_tenant_a.* TO 'delta_tenant_a'@'%';
```

运行账号只能访问自己的库；DDL、备份和迁移由受限运维流程执行。不能把客户 A 的数据库账号写入客户 B 的注册条目。

初始表结构应按最新源码的初始化、迁移和 `DatabaseCompatibility` 等价流程创建；不能只导入旧 `delta_game.sql` 后直接开放。启动时会逐租户检查新增表、列和索引。

## 4. 迁移顺序

1. 读取该客户生产版本的数据库和文件备份，在自己的隔离环境验证恢复。
2. 创建独立目标库、受限账号、租户配置和域名映射；先用合成数据启动共享组。
3. 在维护窗口停止旧实例业务写入、排空任务和聊天，切换支付回调到已验证的接收策略。
4. 导入数据、同步文件、核对记录量和余额/支付/退款/提现账务；旧库停止写入后才能切换路由。
5. 先由客户确认安装/启用，完成登录、下单、派单、聊天、支付回调、退款、提现和文件验收。
6. 观察期结束后停止旧 Java、MySQL、Redis 运行服务，保留备份。不能删除旧数据作为验收动作。

正式切换前必须实现并验证支付回调维护接收、数据库迁移状态和租户路由代次；当前代码只提供运行时隔离基础，未完成生产迁移工具。

迁移文件可用 `deploy/migration/file_delta.py compare/sync/verify` 生成 SHA-256 差异报告，默认 dry-run，复制不删除目标额外文件；财务可用 `deploy/migration/financial_reconciliation.py audit` 对指定租户库执行只读钱包、交易、支付、退款、提现和结算一致性检查。两项工具已在 742 暂存 clone 验证，但不能替代维护窗口中的逐笔微信账单核对和客户确认。

## 5. 更新方式

尚未迁移的客户继续使用现有客户自助更新流程。共享服务组不能继续让客户分别安装后端；共享程序应按服务组统一发布和验证，客户只决定有权限功能的启用。这个规则变更仍需用户确认，不能在本文档中视为已经批准。

现有 `worker.py` 按单实例签名计划安装，不能直接用于共享服务组。新的发布执行器必须绑定服务组、制品摘要、数据库兼容范围和审计记录，不接受任意服务器命令或路径。

当前已提供 `deploy/updater/shared_release.py` 的发布计划验签和 dry-run，以及 `deploy/updater/shared_worker.py` 的 `execute`/`recover`：它会核对服务组、启用租户集合、维护窗口、schema=1、备份要求、三个制品摘要和 GitHub Release 标签；执行时逐租户备份、按后端/后台/H5 顺序健康检查，失败恢复原 Compose 覆盖和版本，回退失败保留维护门禁。执行器仍未在真实共享 Compose 项目完成安装、跨版本回退和逐租户迁移状态演练，不能因为 dry-run 或暂存备份/健康检查通过就启用共享模式。

- 域名、证书、微信回调、公众号和小程序配置逐客户核对。
